Отличный план! Давайте разберем иерархию объектов в GOAL, особенно процессы и сущности. Я структурирую ответ по запрошенному вами формату.

### Общий обзор архитектуры

В GOAL используется объектно-ориентированная архитектура, построенная вокруг **процессов** (`process`), которые являются основными исполняемыми единицами. Процессы организованы в деревья, могут приостанавливаться (`suspend`) и управляются **ядром** (`kernel`). **Сущности** (`entity`) и **акторы** (`actor`) — это специализированные типы процессов, которые представляют игровые объекты.

---

### `/kernel/gkernel-h.gc` - Ядро и базовые типы

**Назначение:** Определяет фундаментальные типы для системы процессов, потоков и планирования.

#### `kernel-context`
*   **Описание:** Глобальный контекст, хранящий состояние диспетчера процессов (планировщика).
*   **Ключевые поля:**
    *   `current-process`: Текущий выполняемый процесс.
    *   `prevent-from-run`: Маска, определяющая, какие процессы не должны запускаться.
    *   `next-pid`: Счетчик для назначения уникальных ID процессам.

#### `process-tree` (Базовый класс для `process`)
*   **Описание:** Базовый класс для организации процессов в дерево (левый потомок, правый брат). Хранит информацию об иерархии и маску состояния.
*   **Ключевые поля:**
    *   `name`: Имя процесса (обычно `symbol`).
    *   `mask`: Битовое поле (`process-mask`), определяющее поведение процесса (например, `execute`, `pause`, `sleep`).
    *   `parent`, `child`, `brother`: Указатели для построения дерева.
    *   `ppointer`: Указатель на указатель процесса. Критически важен для handle'ов и перемещения процессов в памяти.

#### `process` (Наследует от `process-tree`)
*   **Описание:** Основной исполняемый объект. Имеет состояние, поток управления, стек и кучу.
*   **Ключевые поля:**
    *   `status`: Текущее состояние процесса (`dead`, `running`, `suspended` и т.д.).
    *   `pid`: Уникальный идентификатор процесса.
    *   `main-thread`, `top-thread`: Потоки выполнения процесса.
    *   `state`, `next-state`: Текущее и следующее состояние State Machine.
    *   `stack-frame-top`: Вершина стека фреймов (для `catch`, `protect`, `state`).
    *   `heap-base`, `heap-top`, `heap-cur`: Управление памятью процесса.
    *   `entity`: Ссылка на `entity-actor`, если процесс порожден из него.
    *   `trans-hook`, `post-hook`, `event-hook`: Функции-обработчики.

#### `cpu-thread` (Наследует от `thread`)
*   **Описание:** Реализация потока, которая может быть приостановлена и возобновлена. Сохраняет контекст (регистры, стек).
*   **Ключевые поля:**
    *   `pc`: Счетчик команд (Program Counter).
    *   `sp`: Указатель стека (Stack Pointer).
    *   `stack-top`: Верхушка стека.
    *   `stack-size`: Размер стека.
    *   `rreg[7]`, `freg[8]`: Массивы для сохранения регистров общего назначения и чисел с плавающей точкой при приостановке.
    *   `suspend-hook`, `resume-hook`: Функции для приостановки и возобновления.

#### `state` (Наследует от `protect-frame`)
*   **Описание:** Представляет состояние в State Machine процесса. Содержит функции-обработчики.
*   **Ключевые поля:**
    *   `code`: Основная функция, выполняемая в состоянии (может `suspend`).
    *   `trans`: Функция, вызываемая перед `code` при возобновлении процесса.
    *   `post`: Функция, вызываемая после приостановки `code`.
    *   `enter`: Функция, вызываемая при входе в состояние.
    *   `exit`: Функция, вызываемая при выходе из состояния.
    *   `event`: Обработчик событий для этого состояния.

#### `dead-pool` и `dead-pool-heap`
*   **Описание:** Пуллы ("пулы смерти") для переиспользования процессов. `dead-pool` — фиксированного размера, `dead-pool-heap` — с динамическим выделением памяти и компакцией.

#### `handle`
*   **Описание:** Безопасная ссылка на процесс. Содержит `ppointer` и `pid` для проверки валидности, так как процесс мог быть уничтожен или перемещен в памяти.

---

### `/kernel/gkernel.gc` - Реализация ядра

**Назначение:** Содержит логику диспетчеризации процессов, управления потоками и пулами.

#### **Процессы и их жизненный цикл:**

1.  **Создание:** `(process-spawn ...)` или `(get-process pool type size)`. Процесс выделяется из `dead-pool`.
2.  **Активация:** `(activate process dest name stack-top)`. Процесс добавляется в дерево (`*active-pool*`), ему назначается `pid`, создается главный поток.
3.  **Планирование:** Функция `kernel-dispatcher` в цикле обходит дерево `*active-pool*` и для каждого готового процесса:
    *   Вызывает `trans-hook`.
    *   Вызывает `resume-hook` у главного потока (если код не "спит").
    *   Поток выполняется до тех пор, пока не вызовет `suspend` или не завершится.
    *   Вызывает `post-hook`.
4.  **Приостановка (`suspend`):** Поток сохраняет свои регистры и стек в специальную область памяти, затем возвращает управление диспетчеру.
5.  **Возобновление (`resume`):** Диспетчер восстанавливает регистры и стек потока из сохраненной области и передает ему управление.
6.  **Уничтожение:** `(deactivate process)`. Процесс возвращается в `dead-pool`, все его ресурсы освобождаются.

#### **Связь с системой:**
*   Ядро (`*kernel-context*`) управляет всем жизненным циклом.
*   `*active-pool*` — корневой узел дерева всех активных процессов.
*   `*listener-process*` — специальный процесс для выполнения команд из REPL.

---

### `/kernel/gstate.gc` - Система состояний (State Machine)

**Назначение:** Предоставляет макросы и функции для управления состояниями процессов — мощный инструмент для организации игровой логики.

#### **Ключевые макросы и функции:**

*   `(defstate state-name ...)`: Макрос для объявления нового состояния.
*   `(go state-name ...)`: Макрос для перехода в другое состояние *изнутри* процесса.
*   `(go-process proc state-name ...)`: Переход в состояние для другого процесса.
*   `enter-state`: Низкоуровневая функция, которая выполняет переход между состояниями (вызывает `exit` старого, `enter` и `trans` нового, запускает `code`).

#### **Как состояния связаны с процессами:**
Процесс (`process`) хранит указатели на свое текущее и следующее состояние (`state`, `next-state`). При вызове `go` устанавливается `next-state`, и в подходящий момент (часто при следующем запуске процесса) вызывается `enter-state` для выполнения перехода. Состояние само является `stack-frame`, что позволяет корректно обрабатывать его выход через `exit` при нелокальном выходе (например, `throw`).

### `/entity/actor` (Обобщенная концепция)

**Назначение:** Актор — это игровой объект, который обладает представлением в мире (позиция, анимация, физика) и поведением (логикой). В коде это обычно процесс, наследованный от `process` (или подобного), с дополнительными полями для игровой логики.

*   **Поля (добавляются к полям `process`):**
    *   `pos`, `rot`: Позиция и вращение в мире.
    *   `scale`: Масштаб.
    *   `color`: Цвет.
    *   `mesh`, `joints`: Графическое представление (модель, скелет).
    *   `collider`: Объем для обработки столкновений.
    *   `state-time`: Время, проведенное в текущем состоянии (полезно для анимаций и таймеров).

#### **Связь между `entity` и `process`:**
`entity` (например, `entity-actor`) — это тип, который часто спавнится из данных уровня. При спавне создается соответствующий `process` (например, `actor`), и в его поле `entity` записывается ссылка на породившую его сущность. Это позволяет разделить данные, определенные в уровне, от динамического поведения, реализованного в процессе.

---

### Итог: Как все работает вместе

1.  **Уровень загружается.** Данные об `entity` считываются из файла.
2.  **Создаются процессы.** Для каждой `entity` создается процесс-`actor` из соответствующего `dead-pool-heap`. Ссылка на `entity` записывается в поле `entity` процесса.
3.  **Процесс активируется.** Он добавляется в дерево `*active-pool*` (например, в `*entity-pool*`).
4.  **Диспетчер ядра находит процесс.** На каждой итерации игрового цикла `kernel-dispatcher` обходит дерево процессов. Для каждого процесса, чья маска не блокирует выполнение, он:
    *   Вызывает `trans-hook` (если есть).
    *   Возобновляет выполнение главного потока (`cpu-thread`), который выполняет функцию `code` из текущего `state`.
    *   Код работает до вызова `suspend`.
    *   Вызывает `post-hook` (если есть).
5.  **Логика реализуется через состояния.** Внутри своего `state`-кода актор может:
    *   Читать данные из своей `entity`.
    *   Обновлять свою позицию (`pos`).
    *   Взаимодействовать с другими акторами через `send-event`.
    *   Менять состояние с помощью `go`.
6.  **При уничтожении** вызывается `deactivate`, процесс возвращается в пул, и цикл завершается.

Таким образом, **процессы** — это "души" игровых объектов, **ядро** — это "сердце", которое их оживляет и управляет ими, а **сущности/акторы** — это конкретные реализации игровых объектов, объединяющие логику (процесс) и данные (поля актора). **Состояния** предоставляют удобный способ организации сложного поведения внутри процесса.

## Различие между Процессом, Состоянием и Конечным Автоматом

### 1. Процесс (`process`)
**Что это:** Исполняемая единица в системе, аналог "актора" в actor model.

**Характеристики:**
- Имеет собственный поток выполнения (`cpu-thread`)
- Управляется ядром (планировщиком)
- Может приостанавливаться (`suspend`) и возобновляться
- Имеет собственную память (кучу процесса)
- Организован в дерево процессов
- Может получать и обрабатывать события

**Пример в коде:**
```lisp
(defbehavior example-behavior process ()
  "Пример поведения процесса"
  (loop
    (format #t "Process is running~%")
    (suspend))) ; Отдает управление на один кадр
```

### 2. Состояние (`state`)
**Что это:** Контейнер для поведения процесса в определенный момент времени.

**Характеристики:**
- Является **частью** процесса
- Определяет набор функций-обработчиков:
  - `enter` - при входе в состояние
  - `exit` - при выходе из состояния  
  - `trans` - перед выполнением кода
  - `code` - основная логика
  - `post` - после приостановки кода
  - `event` - обработка событий
- Наследуется от `protect-frame` (имеет cleanup-функцию)

**Пример в коде:**
```lisp
(defstate idle-state process
  :enter (lambda () (format #t "Entering idle~%"))
  :code (behavior ()
          (loop
            (format #t "Idling...~%")
            (suspend)))
  :exit (lambda () (format #t "Exiting idle~%")))
```

### 3. Конечный Автомат (State Machine)
**Что это:** **Паттерн управления**, реализованный через взаимодействие процесса и его состояний.

**Характеристики:**
- Это не отдельный объект, а **способ организации кода**
- Состоит из:
  - Процесса-владельца
  - Набора состояний
  - Механизма переходов между состояниями (`go`)
- Управляет поведением процесса во времени

**Пример в коде:**
```lisp
(defbehavior enemy-ai process ()
  "Конечный автомат врага"
  (go patrol-state) ; Начальное состояние
  
  ;; Сам процесс просто запускает автомат
  ;; Дальше управление осуществляется через состояния
  )

(defstate patrol-state process
  :code (behavior ()
          (loop
            (patrol-area)
            (when (sees-player?)
              (go chase-state)) ; Переход в другое состояние
            (suspend))))

(defstate chase-state process  
  :code (behavior ()
          (loop
            (chase-player)
            (when (lost-player?)
              (go patrol-state)) ; Возврат в патрулирование
            (suspend))))
```

## Аналогия

- **Процесс** = Актер в театре (исполнитель)
- **Состояние** = Роль, которую играет актер (Гамлет, Офелия)
- **Конечный автомат** = Сценарий пьесы (последовательность сцен и переходов)

**Ключевое понимание:** Процесс — это контейнер для выполнения, состояние — это конкретное поведение в данный момент, а конечный автомат — это паттерн, который организует смену состояний для создания сложного поведения.

## 🎯 Трехуровневая архитектура GOAL

### **1. Системный уровень (Планировщик и процессы)**

**Процесс (`process`) = Виртуальный поток + контекст выполнения**

```lisp
;; Процесс - это контейнер для выполнения кода
(define *my-process* 
  (new 'global 'process 'my-process 4096))

;; Активируем процесс (добавляем в планировщик)
(activate *my-process* *default-pool* 'my-process *kernel-dram-stack*)

;; Устанавливаем код для выполнения
(set-to-run (-> *my-process* main-thread) my-main-function)
```

**Что содержит процесс:**
- `main-thread` - виртуальный поток выполнения
- `status` - состояние (running, suspended, dead)
- `heap` - собственная память
- `stack-frame-top` - стек вызовов
- `state` - текущий FSM-стейт

### **2. Уровень конечных автоматов (FSM контейнеры)**

**Состояние (`state`) = Контейнер поведения + данных**

```lisp
;; FSM состояние - это набор методов + данные
(defstate patrol-state entity-actor
  :enter (lambda () 
           (format #t "Starting patrol at ~A~%" (-> self patrol-point)))
  :code (behavior ()
          (loop
            (patrol-to-next-point)
            (when (sees-player?)
              (go chase-state))  ; Смена FSM состояния
            (suspend)))          ; Возврат к планировщику
  :data (patrol-points [...]    ; Данные состояния
         current-target 0))
```

**Ключевой момент:** Когда процесс выполняет `(go new-state)`, он меняет **только FSM-состояние**, но остается тем же процессом!

### **3. Уровень игровых объектов**

**Entity-Actor = Игровой объект + бизнес-логика**

```lisp
(deftype enemy-actor (entity-actor)
  ((health int32)
   (speed float)
   (weapon basic)
   (target process)))

(defbehavior enemy-actor-init enemy-actor ()
  "Инициализация игрового объекта"
  (set! (-> self health) 100)
  (set! (-> self speed) 2.5)
  (go patrol-state))  ; Запускаем FSM
```

## 💡 Ключевые отличия

| Уровень | Что меняется | Частота смены | Пример |
|---------|--------------|---------------|---------|
| **Процесс** | Контекст выполнения (поток) | Редко (создание/уничтожение) | `(process-spawn enemy-type ...)` |
| **FSM Состояние** | Поведение + данные | Часто (игровая логика) | `(go patrol-state)` → `(go chase-state)` |
| **Игровой объект** | Данные объекта | Постоянно | `(set! (-> enemy health) 50)` |

## 🎮 Практический пример

```lisp
;; УРОВЕНЬ 1: Создаем системный процесс
(let ((enemy-process (process-spawn enemy-actor 
                                   :from *nk-dead-pool*
                                   :to *entity-pool*)))
  
  ;; Процесс теперь в планировщике ядра
  ;; Ядро будет периодически запускать его main-thread
  
  ;; УРОВЕНЬ 2: Процесс запускает FSM
  (run-now-in-process enemy-process enemy-actor-init)
  
  ;; УРОВЕНЬ 3: FSM работает с данными игрового объекта
  ;; Внутри enemy-actor-init:
  ;; (go patrol-state) → FSM начинает работу
  ;; patrol-state.code работает с (-> self health) и т.д.
)
```
